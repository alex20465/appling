# @appling/ide

The repo view of [Appling Desktop](../desktop): the IDE server that Desktop runs once per repo and the client its view of the repo loads, with the model canvas as the main area, the search, the inspector and the editor folded behind **Source**. It is private, an internal part of Desktop, which bundles it (`scripts/bundle.mjs` of `@appling/desktop`); there is no standalone browser IDE any more. See https://appling.tools/docs/tools/desktop/.

```sh
node packages/ide/out/server/main.js [folder] [--port 4410] [--origin <url>]... [--shared-sessions]
```

Desktop starts it with an IPC channel and `--port 0`: the server reports `{ type: 'ready', url }`, the model errors, the unsaved files, the unseen changes and the implementation marks over IPC, and ends when the channel closes. With `--shared-sessions` it takes the agent sessions, the playbooks and the app host of the workspace from Desktop over the same channel. It serves the folder's `.appling` files on `127.0.0.1` and only answers pages it served itself; `--origin <url>` (repeatable) trusts another origin too, the local end of a port Desktop forwards from a remote repo. Run without IPC it still serves the client, for development only.

`vite.demo.config.ts` builds the same client as the browser demo of the landing site (https://appling.tools/ide/) into `dist/demo`: `src/demo/api.ts` answers every server call in the page and the language server runs in a worker. Edits stay in the page until you reload; generation and the review of commits need Desktop.

## What you get

- A text editor (Monaco) backed by the Appling language server: diagnostics, completion, hover, go to definition, references, rename and formatting. Ctrl+S (Cmd+S) saves.
- The model canvas, a tree that grows from a seed and unfolds on click: modules, then the declarations of the lens (Domain, Behavior, Application, Interfaces or Access), then what uses each declaration, grouped by kind. Each circle shows its name, kind and one fact; relevance decides its size and place, so the core of the business stands out. Clicking a circle unfolds and inspects it.
- The lens and the link entities option (`entity link`, such as join records, hidden by default) are saved in `.appling/view.json`.
- Search over every element (entities, fields, actions, machines, queries, use cases, endpoints, pages and more), grouped and filtered by layer.
- Selection in sync: moving the cursor selects the element on the canvas and in the inspector; clicking a circle, a search result or the inspector reveals the text.
- For actions the inspector shows which actors may trigger them and which invariants they put at risk, for machines which states are reachable and how, answered by the simulator.
- An inspector that explains the element: for an action what it does (input, requires, changes, errors), for an entity its actions with the transitions they drive, for an actor what that person may do (actions, pages with the actions they offer, use cases, queries, data) and the policies that decide it, where it is implemented (its code references, with the lines), then its members and what uses it and what it uses, grouped by layer and with the members each link runs through. You also edit the model there: rename, change a type, set any property, add a member from its source text, or remove the element.
- Every edit goes through the Appling edit operations: the touched text is printed canonically, the edit is rejected with the reasons when it would introduce errors, and it lands in the editor as one undoable step. Renames follow references, expressions, `does` texts, exports and message keys.
- A Review tab for a workspace in git: the model diff between any commit (the uncommitted changes by default) and the working tree, marked on the canvas with removed elements ghosted where they were, the changed files and a text diff per element or file.
- Once a release exists (`appling release`), the header shows how many migration steps were recorded since; renames, type changes and removals of released domain elements add them automatically.
- Live changes: every model change, by an agent session or any process that writes the files, is marked on the canvas (added, changed, removed ghosted) without moving the camera, and listed in the Changes tab per file with the session that wrote it, its model and text diff, Accept and Revert. The baseline is the text last accepted, starting with the files on disk when the server starts; `onUnseen` reports the count (Appling Desktop marks the repo in the rail).
- The visual tools of agent sessions draw on the canvas: each session's view and bubbles wait as a chip until you open them, and `propose_edits` is decided in the Changes tab.
- The playbook: the Playbook tab lists the chapters agent sessions write about their plans and work, with each session's colour and label, and plays them on the canvas only when you step forward (planned steps dashed, done steps solid, added, changed and removed elements marked). Chapters that arrive meanwhile queue; approve, reject or comment on a step and the session that wrote it gets it as a message (`/api/playbook`, `/api/playbook/position`, `/api/playbook/respond`, the `playbook` message on `/events`, `Ide.playbooks`). A view may name its workspace (`?workspace=` on `/api/playbook` and `/events`, `workspace` in its context report), as Appling Desktop does for a folder in several workspaces; it then gets that workspace's playbook. A chapter's **diff** from another repo of the workspace asks Desktop to open that repo's Changes tab (`applingDesktop.showChanges`, heard there through `onShowChanges`).
- Seed to code: the editor marks every model line with the implementation state of the element it declares (implemented, partial, unimplemented, shifted, broken) and the canvas marks each declaration; a click on a mark opens the element's code. Declaring lines that are no elements (use case steps and handlers, `requires`, page components, navigation items, messages) have sub-anchor addresses (`sales.Checkout#step[2]`): the snapshot holds their locations, code references and states (`Snapshot.anchors`), their lines get marks, and selecting one shows its element on the canvas and the line's own code in the Inspector. A changed element selected on the canvas offers **text diff** in the Inspector: the Review's text diff (in Desktop's code view through `openTextDiff`), or the live file diff in the Changes tab. The Code tab generates through the targets of `appling.config.json` (what changed since the last generation, the selected element, checked elements or everything) in a worker (`POST /api/generate`, `GET /api/generation`, the `generation` and `generation-event` messages on `/events`), offers it after a model change, writes a playbook chapter per run, and lists the registry tasks with the agent session that claimed each. `GET /api/code` serves code files read only; `onImplementation` reports the marks and code links (Appling Desktop's code view shows them).
- The repo's MCP server at `/mcp` for agent sessions (bearer token per session, `POST /api/sessions` opens one): agents label their work, set their status, claim elements and files and message each other; the canvas rings the claimed elements in the session's colour. A question typed in a session's view on the canvas reaches its inbox (`POST /api/sessions/<id>/ask`).

The views and the files update when the files change on disk.
