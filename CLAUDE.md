# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Appling: a declarative DSL (`.appling` files) that models a business application across five layers (Domain, Behavior, Application, Interfaces, Experience) plus cross cutting concepts (modules, roles, actors, tenants, migrations). The text is the canonical source of truth; the end goal is a validated semantic graph for visualization, simulation and AI editing; code generation produces a draft project for a target framework through installable extensions (Django and Ash first). `docs/concept.md` is the design spec (layer ownership, reference rules, narrowing, identity by qualified name) and is the authority when grammar or validation decisions are unclear. `docs/ROADMAP.md` lists the planned packages, phases and decisions.

## Commands

pnpm workspace (`packages/*`), Node 24 (`.nvmrc`), TypeScript 7, Langium 4.4, vitest 5. There is no linter. Use the pinned pnpm (`corepack pnpm`); a global pnpm 8 cannot install into this workspace. `pnpm-workspace.yaml` lists packages exempt from the minimum release age; a newly published dependency needs an entry there.

```sh
pnpm install
pnpm build                  # every package in dependency order (langium generate + tsc in lang, vite for the IDE client, astro for landing)
pnpm check [paths...]       # validate .appling files (default: current dir, recursive)
pnpm fmt [paths...]         # rewrite files into canonical form
node packages/cli/out/main.js graph [paths...]   # semantic graph as JSON
pnpm test                   # vitest over packages/*/test
pnpm vitest run packages/lang/test/validation.test.ts -t "name"   # one file, one test
pnpm vitest run -u          # update snapshots (model, codegen-django, codegen-ash)
node scripts/bench/check-scaling.mjs [copies...]   # time `check` on N copies of examples/ (catches superlinear validation)
node scripts/bench/ai-modeling.mjs [--model sonnet] [--runs 1] [--brief name] [--keep]   # a fresh claude -p writes models from scripts/bench/briefs/ with only docs/language; scored by check
node packages/desktop/out/bin.js examples       # Appling Desktop on the sample models (needs a display; ask the user to start it)
pnpm --filter @appling/lang build   # rebuild only the language after grammar changes
node scripts/ci/codegen-coverage.mjs   # codegen coverage of every extension over the constructs fixture and examples (--json, --markdown, --base, --root, --badge)
node scripts/ci/codegen-e2e.mjs <django|ash|go|rust>   # generate examples + constructs fixture, build them with the real toolchain
scripts/ci/codegen-e2e-docker.sh <target>             # the same in the target's official docker image (projects in .e2e/)
pnpm sandbox <ide|openvscode|vscode|desktop>           # a UI sandbox on a copy of examples/ with DevTools on 9222 for the `sandbox` MCP server (ask the user to start it; skill ui-sandbox)
```

CI: `.github/workflows/ci.yml` on every PR and push to `main` runs build, test, `check examples` and the `fmt examples` + `git diff --exit-code` idempotence check, then the codegen coverage report (head and base, one sticky PR comment marked `<!-- appling-codegen-coverage -->`, the badge JSON pushed to the `badges` branch on `main`); see `docs/contributing/development.md`.

`check` and `fmt` run the built CLI (`packages/cli/out/main.js`), so rebuild after any source change. Tests live in `packages/<pkg>/test/`; `packages/lang/test/workspace.ts` builds in memory sources as one workspace. The lang tests import `src/` and only need `langium generate`; every other package's tests import `@appling/*` through the packages' `out/` exports, so rebuild a changed upstream package before testing downstream ones. Every validation rule has a negative fixture in `validation.test.ts`; add one with each new rule. `packages/lang/test/fixtures/constructs/` uses every AST type and keyword of the grammar (`constructs.test.ts` fails otherwise), so extend it with each grammar change; each codegen extension's `coverage.test.ts` plans it and fails when its coverage per node kind (`test/coverage.json`) drops, and `-u` raises the baseline after a gain. Use `pnpm check examples` to verify changes against the sample models; `examples/sales.appling` and `examples/crm.appling` reference each other across modules.

CI: `.github/workflows/codegen-e2e.yml` runs `scripts/ci/codegen-e2e.mjs` once per target (PRs touching codegen, lang, model, cli or examples; nightly; on demand). A generated project that fails to build, warns or fails a test is a generator bug: fix it in the extension with a snapshot or unit test.

## Architecture

- `packages/lang` (`@appling/lang`): the language. `src/appling.langium` is the grammar; `langium generate` writes `src/generated/` (gitignored, never edit). `index.ts` exports the services factory, the printer and the generated AST. `lsp.ts` (subpath export `@appling/lang/lsp`) adds Langium's LSP services with the canonical formatter and a hover; `language-server.ts` is the `appling-language-server` stdio binary.
- `packages/model` (`@appling/model`): the semantic graph. `buildGraph(models, services)` turns resolved models into serializable nodes (qualified name, kind, layer, zoom level, module, props) and edges (`contains`, `uses` for names in expressions, plus one per cross reference, kind = reference property, `decl` becomes `type`); `dependencies(graph)` aggregates module to module edges; `relevance(graph)` (subpath `@appling/model/relevance`, browser safe) scores modules and top level declarations from their dependents and dependencies, mapped into the range of a declared `core`/`supporting`/`peripheral` level (own or inherited from the module, `props.relevance`); `diffGraphs(before, after)` (subpath `@appling/model/diff`, browser safe) lists added, changed (props or edges other than `contains`) and removed elements by qualified name, mapping renames through the migration steps only the graph after has, and `withRemoved` puts removed elements back for a ghosted drawing. Only the kinds in `NAMED` and those with a `keyOf` key become nodes; every other AST node folds into its element's props as canonical text, and its references become edges of that element. A new grammar element kind must be added to one of the two. Declaring lines that are no elements (use case steps and their handlers, `requires`, page components, navigation items, messages) get sub-anchor addresses in `graph.anchors` (`anchors.ts`, subpath `@appling/model/anchors`: `sales.Checkout#step[2]`, `#step[2].on[Declined]`, `#requires[1]`, `#component[1]`, `#item[A/B]`, `#message[key]`), which carry code references and a state (`anchorStates`) without being nodes; a new such line kind goes into `subAnchors`.
- `packages/codegen` (`@appling/codegen`): code generation core. An extension (`CodegenExtension`) maps each graph node to `command`, `template` and `task` steps (`undefined` = unsupported, `[]` = covered by a parent); `plan` orders them by layer and builds one registry entry per node; `runPlan` executes them into the output folder and writes `.appling/tasks.json`. Extensions may add `setup(context)` steps that run once first, and a step `phase` to run after all earlier phases. Extensions read only `GraphNode.data` (structured, references as qualified names, expressions as typed trees), never the Langium AST. Targets come from `appling.config.json` (`generate: [{ extension, out, options }]`). `migrate.ts`: `pendingChanges` turns the model's migration steps (not yet in the project's `.appling/migrations.json`) into changes with the element's qualified name before and now; extensions map each with `migrate(change, context, files)` (each extension's `migrations.ts`); tasks go to the changed element's registry entry. Seed to code (#20): `runPlan(..., written)` collects what each step wrote (`written.ts`: the main run of added lines of a template, the `creates` of a command), `recordWritten` locates it in the final files as code references and records each element's `fingerprint` per target in the workspace's `.appling/generation.json`; `generate.ts` (`generateElements`) generates a selection (outstanding, elements, all) into every target, creating it or merging only the selected elements' files (`mergeGeneration` with a `MergeScope`), and `workspaceImplementation` gives every element its state (`implementationStates` of `@appling/model/implementation`: implemented, partial, unimplemented, shifted, broken).
- `packages/codegen-django` (`@appling/codegen-django`): Django extension. `python.ts` translates expression data to Python (`python`) and to `models.Q` (`q`); `index.ts` dispatches node kinds to `models.ts` (L1), `behavior.ts` (actions, errors, events, machines, jobs), `application.ts` (queries, serializers, externals, use cases) and `api.ts` (REST framework views and routes). `files.ts` merges imports into generated Python files (`pythonFile`); `tests.ts` writes skipped test skeletons whose bodies are registry tasks. Tests apply the template steps in memory; an end to end run needs `uv` and network.
- `packages/codegen-ash` (`@appling/codegen-ash`): Ash extension. `elixir.ts` translates expression data to Ash `expr` bodies and builtin validations; `index.ts` maps nodes to `mix igniter.new` / `ash.gen.*` commands and patches the generated resources (defaults, identities, calculations, validations). Relationships use phase 1 so every resource exists first; every patch of an existing module (`patch()` in `naming.ts`) runs in phase 2, after the last `mix` command, so expressions may follow relationships. `resource.ts` adds lines to (nested) DSL sections and extensions. `behavior.ts` (actions, AshStateMachine, AshOban), `application.ts` (read actions, calculations), `api.ts` (AshJsonApi with a Plug router and Bandit) and `tests.ts` (skipped ExUnit tests).
- `packages/ide` (`@appling/ide`, private): the repo view of Desktop, the VS Code extension and `appling ide`, the IDE server each runs per repo and its client (published because the CLI depends on it; `appling ide [folder]` starts it through `startIdeProcess` and opens the client in the browser). Subpaths `./process` (`startIdeProcess`) and `./host-requests` (`diffMessage`, `openMessage`) serve both apps; in an iframe opened with `?host=frame` the client takes its host hooks over `postMessage` (`src/client/frame-host.ts`, also the host's `theme`: `--appling-*` tokens over the IDE's, `data-theme="light"` for the light palette of `styles.css`), a host with `openSource` hides **Source**, a host with `panels` draws the side panels itself (`src/shared/panels.ts`, `@appling/ide/panels`: the client sends `PanelState` and takes `PanelAction`s), the server sends `frame-ancestors` and takes `{ type: 'trust', origin }` over IPC. `src/server` (tsc to `out/`) serves the built client, `/api/snapshot` (files, graph, dependencies, source locations), `/api/file`, `/api/view` (canvas lens and link entities option in `.appling/view.json`), `/api/edit` (runs `applyEdit` on the texts the client sends, with the latest release; writes nothing), `/api/release`, `/api/diff?rev=` (`src/server/git.ts`: the model at a commit through `git ls-tree`/`git show` and the same build, compared with the working tree, plus the changed files from `git diff --name-status` and `git status --porcelain`), `/api/diff/file`, `/api/revisions`, `/mcp` (the repo's MCP server per agent session, bearer token; `/api/sessions` opens, renames and ends sessions; `--shared-sessions` takes the store and an `AppHost` from Desktop over IPC) and websockets `/events` (snapshot pushes on file changes, `sessions` and `act` pushes, the client's `context` reports) and `/lsp` (one Langium language server per connection); it binds 127.0.0.1 and checks Host and Origin. `src/client` (React, Monaco with its bundled LSP client, built by Vite to `dist/client`) takes its view logic, tree layout and model canvas from `@appling/viz`; the canvas is read only, `Search.tsx` and `Inspector.tsx` in the side panel open every other element. The client always has Desktop's layout: the canvas as the main area, the editor behind **Source** (`SOURCE_OPEN` of `api.ts`, true in the demo). The Review tab (`Review.tsx`) shows that diff and marks it on the canvas over `withRemoved`; its text diffs go to `window.applingDesktop.openTextDiff` when a host provides it (`hooks.ts`, the Code OSS view of #8), else into the panel. `live.ts` (`LiveTracker`) marks every model change against a baseline (the text last accepted per file, starting with the disk at server start), attributes files written by a session's MCP tool calls, and accepts or reverts per file (`/api/live/*`, Changes tab); `visuals.ts` (`AgentViews`) is the canvas `VisualHost` of each session's `/mcp`: views and bubbles wait as chips until the user opens them (`AgentView.tsx`), `propose_edits` waits for `/api/proposals/<id>`. `generation.ts` (`GenerationRunner`) runs one generation at a time in a worker thread (`generation-worker.ts`, package imports only so Node runs it from `src/` under the tests; it carries the four stacks' extensions, used when the project has none installed; `POST /api/targets` adds a stack's target through `addTarget`) for `POST /api/generate`, pushes `generation` and `generation-event` over `/events`; the snapshot carries `implementation`, `targets` and `tasks`, the Code tab (`Implementation.tsx`) generates and lists the registry tasks with their claiming session, the editor draws gutter marks (`lineMarks`) and `CodeView.tsx` shows code read only (`/api/code`) when no Desktop code view opens it; `onImplementation` reports marks and code links, which Desktop forwards to the Appling extension over the code bridge. `POST /api/sessions/<id>/ask` delivers a question typed in a session's view to its inbox. Edits from the inspector go to `/api/edit`; the returned text edits are applied to the Monaco models as undoable steps (`applyTextEdits`) and saved. A model is dirty while its text differs from the last disk text. Shared types and `buildSnapshot` (the snapshot from file texts) live in `src/shared`. Design tokens follow the landing site. `vite.demo.config.ts` builds the browser only demo into `dist/demo` (base `/ide/`): it aliases the client's `./api.js` to `src/demo/api.ts`, which keeps `examples/` in memory, answers every server call in the page (edits through `@appling/model/edit`) and runs the language server in a worker (`src/demo/language-server.ts`).
- `packages/viz` (`@appling/viz`): views and canvases. `views.ts` is the pure, tested view logic of the IDE client (`growTree`: the dependency tree of one lens of `LENSES`, domain, behavior, application, interfaces or access, from a seed over modules and the lens's declarations to what uses each unfolded declaration, grouped by kind and ordered by relevance, search, relations by layer with the members they run through, entity actions, action summaries, `trailOf`: the tree that draws only the elements the AI shows one after another, each unfolded in place, the flowcharts `flowView` of a machine or a use case, and the card views `cardView`: one card per action or event); `layout.ts` places the tree growing upwards (rows centered on the most relevant, big folded groups wrapped) and the flowcharts top down (`layoutFlow`, own ranks, no graph library); `canvas/` the read only canvases (`ModelCanvas`, own SVG with pan, zoom and a camera that follows unfolds, circles sized by relevance; `FlowCanvas`; `CardCanvas` as a card grid; `Bubble.tsx` the AI's note and code bubbles; `canvas.css`). `protocol.ts` holds the types of the visual tools (`Show`, `Bubble`, `Review`, `Decision`, `Selection`, `Status`, `nextShow`). The floating Electron window is gone (7C); agent views draw on the IDE canvas.
- `packages/ai` (`@appling/ai`): `Project` (check, graph, source, edit, registry, tests over a workspace folder), tool definitions with zod schemas in `tools.ts` for the MCP server (`mcp.ts`, bin `appling-mcp`, stdio or `--http`). Tools run against a `ToolContext`: `diskContext` writes files, `ProposalContext` collects edits on a working copy for review. `createMcpServer` always sends `MCP_INSTRUCTIONS` (`prompts.ts`: the model is the source of truth for business logic). With a `visualizer` (a `VisualHost`; only the IDE server's `AgentViews` for an agent session's `/mcp`) it registers `visualTools` (`visual.ts`: `visualize`, `visual_bubble`, `visual_selection`, `visual_reply`, `visual_status`, `propose_edits`, which waits for the decision in the app); the stdio and `--http` servers have no visual tools. `proposal.ts` builds a proposal's text hunks and graph diff. With a `session` (`{ id, store, host }`) it adds the session tools (`session-tools.ts`: label, status, claims, list, messages, `ide_context`, `ide_act`), attributes every call to the session and adds `conflicts` and a `warning` to edits that touch another session's claims. `sessions.ts` holds `SessionStore` (`MemorySessionStore`; `serveSessionStore`/`RemoteSessionStore` share one over an IPC `Channel`). The registry skill text lives once in `skills/appling-registry/SKILL.md` and doubles as the MCP prompt. There is no built in chat and no AI SDK dependency: AI runs through agents in Desktop's terminals (agent sessions).
- `packages/desktop` (`@appling/desktop`, private until the first release, epic #15): Appling Desktop, the Electron app. `bin.ts` (`appling-desktop [folders, remote repos or .code-workspace files]`) starts Electron detached; `main.ts` takes the single instance lock (paths as additional data, `second-instance` opens them), runs the IDE server (`@appling/ide`'s `out/server/main.js <folder> --port 0`) per repo as a child process (`ide-process.ts` over `startIdeProcess` of `@appling/ide/process`; the IDE's `main.ts` reports `{ type: 'ready', url }` and then `{ type: 'status', errors }` after every model change, `{ type: 'status', unsaved }` and `{ type: 'status', changes }` (unseen live changes) over IPC and ends on disconnect; `git.ts` reads the branch from `HEAD` for the rail) and shows one kept alive `WebContentsView` per repo at `<url>/` (the IDE client with the editor folded behind **Source**) next to the shell page (`src/shell`, the rail, through `preload.cts`). `workspaces.ts` holds the pure state (open workspaces, each a VS Code `.code-workspace` file read and written by `code-workspace.ts`, the shown repo per workspace, pinned and hidden repos and the rail order, the collapsed rail, the most recently used order for Ctrl+Tab), `switcher.ts` the fuzzy switcher's ranking (`fuzzyMatch`, `switcherEntries`; the shell draws it while `main.ts` hides the repo views), `session.ts` saves and restores it in `session.json` (with the repos whose code view is open), `agent-sessions.ts` holds the agent sessions of every workspace and serves them to each repo server (`startIdeProcess({ sessions, host })`), `repos.ts` tracks the repos with a server (one per folder, however many workspaces hold it), `rail-status.ts` the rail's status per repo and summed per workspace (each feature reports through its own `rail.source(name)`: validation errors, unsaved files the IDE client reports over `/events`, unseen live changes (a dot on background repos), git state, agent sessions), `clone.ts` runs `git clone` with progress for the clone form, `git.ts` their git state for the rail (`watchGit`: branch, ahead, behind, dirty from `git status --porcelain=v2`), `keybindings.ts` the menu commands and the user's `keybindings.json` over the defaults. The code view (#8, `code-*.ts`): one openvscode-server per repo (downloaded and verified on first use, `code-download.ts`), started lazily or always (`code-instances.ts`), all behind one proxy origin (`code-proxy.ts`, so Code OSS's browser stored settings are shared) in a `WebContentsView` right of the IDE view (`code-view.ts`); the selection syncs through `code-bridge.ts` with `appling-vscode`'s `desktop-bridge.ts` and the repo view's `repo-preload.cts`. Packaging: `scripts/bundle.mjs` bundles the main process and every program Desktop runs (IDE server, pty host, language server, MCP server, CLI) with esbuild into `app/` at the paths of `BUNDLED`, with the preloads and the `appling-vscode` vsix (unpacked, `UNPACKED`) (`resources.ts`; `programPath` falls back to the workspace packages), copies node-pty (N-API, no Electron rebuild) to `app/native/`, and `electron-builder.config.mjs` packs `app/` into AppImage, NSIS and dmg (`pnpm --filter @appling/desktop package --linux`); `updater.ts` runs electron-updater against GitHub Releases, `update-policy.ts` decides `auto`/`manual`/`none` (unsigned macOS only points to the release page); `.github/workflows/desktop-release.yml` builds and publishes on `desktop-v*` tags. Windows (#14): `windows.ts` is the pure window state (which window holds which workspace, panes moved into each, `placement` of every pane, layouts per monitor setup in `session.json`), `displays.ts` the display fingerprint and the fallback placement on the primary display, `panes.ts` the pane abstraction (`paneId`, `registerPaneType` with a region, `layoutPanes`; the repo view is type `ide`, terminals and the code view register their own), `window-host.ts` the thin Electron side (one `BaseWindow` per window with its shell page, pane views moved with `removeChildView`/`addChildView` so nothing reloads). `terminal/` is the terminal panel of each repo (#9), the `terminal` pane: xterm.js (WebGL, unicode 11, search, links, images, OSC 52) in one kept alive `WebContentsView` per repo (`terminal/view`, bundled by esbuild in `build-terminal.mjs`; - `packages/pty-host` (`@appling/pty-host`, private, issues #9 and #18): the per user daemon that owns the terminals so they outlive the app, the way VS Code's ptyHost works. `host.ts` (`PtyHost`) spawns shells (with `attach` the spawning client gets the output from the first byte, `spawnAttached`) with `node-pty`, mirrors each into an `@xterm/headless` terminal and on `attach` replays it with `@xterm/addon-serialize` (the snapshot is taken in a `write('')` callback; output arriving meanwhile is queued for that client, so nothing is lost or doubled); ended terminals keep their scrollback until killed. `protocol.ts` is newline delimited JSON over a Unix socket (Windows: a named pipe) in a 0700 folder (`paths.ts`: `APPLING_PTY_HOST_DIR`, else `$XDG_RUNTIME_DIR` or the temp folder); a client must first send a `hello` with the token the host writes to that folder on every start. `client.ts`: `connectPtyHost` connects or starts the host detached (`main.js serve`, its own session, output to `pty-host.log`), `PtyHostClient`, `AttachedTerminal` (buffers output until the first `onData`). A lock folder lets only one of two hosts started at once listen; the host exits after `--idle-timeout` without authenticated clients and running terminals. `status.ts` keeps each terminal's status from its output (running, `needsInput` after OSC 9/777 until the next input, exited) and `meta` is free spawn metadata; subscribed clients get `terminal`, `status` and `removed` events. With nobody attached to a terminal that needs input the host calls its injected `Notifier` (`notifier.ts`: `systemNotifier`, gdbus or notify-send, osascript, a PowerShell toast); a click runs the `open` command (Desktop: `--session <id>`, `app-flags.ts`), a reply goes to the pty. Status and notifier are transport independent: a remote host runs with `notify: false` and Desktop's `remote/notify.ts` (`RemoteStatus`) raises its notifications locally from the subscribed `status` events. `appling-pty-host list|kill|stop` work without the app; Desktop's `--tray` mode (`tray.ts`) lists and stops sessions too. node-pty is N-API, so the same build loads under Electron with `ELECTRON_RUN_AS_NODE`. Tests start real hosts in temp folders and run against the built `out/main.js`.
- `packages/vscode` (`appling-vscode`, private): the VS Code extension. `scripts/bundle.mjs` bundles `src/extension.ts` (a `vscode-languageclient`) and the language server from `@appling/lang` (CommonJS), the IDE server with its worker and client and the AI skills (`out/ide/`, ESM), the CLI (`out/cli/`) and the agents' hook into `out/`, then `vsce` writes `out/appling.vsix`; the TextMate grammar comes from Langium (`packages/lang/src/syntaxes/`, generated next to the Monarch grammar). Each package has a user facing `README.md` (published to npm) documenting the CLI usage and exit codes, the language overview, its rules and the public API. Keep them in sync when changing CLI behavior, grammar keywords, validation rules or exports from `index.ts`. The full user documentation lives in `docs/` (everything except `concept.md` and `ROADMAP.md` is user facing); `pnpm --filter @appling/landing... build` validates its examples.

Key mechanics that span several files:

- **Identity and migrations.** Elements are identified by their qualified name; there are no separate ids. Migration steps (`rename`/`retype`/`remove`) target a path inside their module as it was before the step. `checkMigration` replays the later steps of the same module (in declaration order) to find where that path lives now, then requires it to exist (rename, retype) or not exist (remove).
- **Scoping** (`appling-scope.ts`). Inside a module, nested elements are visible by dotted path (`Order.status`). Across modules (and files) only members listed in `export` are visible, by module path (`sales.Order`, nested modules `a.b.X`). The scope provider special cases `picks` (fields of the referenced projection), `sort` (fields of the query entity), `set` (fields of the action's entity or the machine's entity) and error handlers (errors of the called action or external op).
- **Layer rules** (`appling-validator.ts`). `LAYER_OF` maps every top level member type to a layer; `checkLayerReferences` walks every cross reference and applies `isAllowed`, which encodes the reference DAG from `docs/concept.md` section 2.3. A new member type must be added to `LAYER_OF`.
- **Expressions** (`appling-types.ts`) are a CEL subset parsed into plain AST nodes. Names inside expressions are strings, not cross references; `ExpressionTyper` resolves them per position (`contextOf`), types every root expression and call, and records `targets` (the element each name stands for). The validator reports its problems; the graph turns targets into `uses` edges; renames must follow them. `actor.is(x)` resolves through `ApplingScopeProvider.lookup`. A new construct that holds an expression needs a branch in `contextOf`, or its expressions are not typed.
- **Edit operations** (`packages/model/src/edit.ts`). `applyEdit(sources, op)` finds the target by qualified name, splices text (rename and retype touch only tokens; add, remove and set reprint the touched element with `printRange`), rebuilds and rejects the edit when it adds an error. Rename has to find every place that names an element; a new way of naming elements (a new reference kind is automatic, but string names like `export` lists, message keys or transition states are not) must be added to `renameSplices`.
- **Releases** (`packages/model/src/release.ts`). `appling release <version>` writes the graph to `.appling/releases/<version>.json`. `applyEdit(..., { release })` appends `rename`/`retype`/`remove` steps for released L1 elements to the module's `since_v<version>` block (`migrationStep`, `appendStep`), mapping current paths back to released ones through that block's renames.
- **Canonical printer** (`appling-printer.ts`). Walks the CST leaves and decides every gap between tokens, keeping comments. `printRange(node)` renders the whole document and returns just one node's canonical text with its surrounding gaps. Layout is driven by the `BLOCKS` (node types whose `{` opens an indented block) and `CLAUSES` (keywords that start their own line inside a block) sets; new block or clause constructs in the grammar must be registered there or they print inline.
- **Scenarios** (`scenario`, outside the layers: `LAYER_OF` gives `cross`, `isAllowed` lets it reference anything). Helpers in `appling-scenario.ts`; the typer types given rows, actor fields, call arguments and checks (`scenarioEnv`). `Simulator.scenario(qn)` runs one; `checkScenarios` in `packages/model/src/scenarios.ts` turns failures into errors, which the CLI's `check` and the MCP `check` tool report once nothing else fails (the validator cannot, `lang` does not depend on `model`). Generators write one test per scenario and skip their guessed tests for `coveredByScenarios(graph)`; `plan` orders scenarios last.

Grammar conventions: keywords that should remain valid as names (fields like `state`, `order`) must also be listed in the `Ident` rule. References use `[Type:QualifiedName]` except for local lookups (`[Field:Ident]`, `[ErrorDecl:Ident]`) that the scope provider resolves.
