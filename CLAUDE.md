# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Appling: a declarative DSL (`.appling` files) that models a business application across five layers (Domain, Behavior, Application, Interfaces, Experience) plus cross cutting concepts (modules, roles, actors, tenants, migrations). The text is the canonical source of truth; the end goal is a validated semantic graph for visualization, simulation and AI editing; code generation produces a draft project for a target framework through installable extensions (Django and Ash first). `docs/concept.md` is the design spec (layer ownership, reference rules, narrowing, identity by qualified name) and is the authority when grammar or validation decisions are unclear. `docs/ROADMAP.md` lists the planned packages, phases and decisions.

## Commands

pnpm workspace (`packages/*`), Node 24 (`.nvmrc`), TypeScript 7, Langium 4.4, vitest 5. There is no linter. Use the pinned pnpm (`corepack pnpm`); a global pnpm 8 cannot install into this workspace. `pnpm-workspace.yaml` lists packages exempt from the minimum release age; a newly published dependency needs an entry there.

```sh
pnpm install
pnpm build                  # every package in dependency order (langium generate + tsc in lang, vite for the inspector client, astro for landing)
pnpm check [paths...]       # validate .appling files (default: current dir, recursive)
pnpm fmt [paths...]         # rewrite files into canonical form
node packages/cli/out/main.js graph [paths...]   # semantic graph as JSON
pnpm test                   # vitest over packages/*/test
pnpm vitest run packages/lang/test/validation.test.ts -t "name"   # one file, one test
pnpm vitest run -u          # update snapshots (model, codegen-django, codegen-ash)
node scripts/bench/check-scaling.mjs [copies...]   # time `check` on N copies of examples/ (catches superlinear validation)
node scripts/bench/ai-modeling.mjs [--model sonnet] [--runs 1] [--brief name] [--keep]   # a fresh claude -p writes models from scripts/bench/briefs/ with only docs/language; scored by check
pnpm --filter @appling/lang build   # rebuild only the language after grammar changes
node scripts/ci/codegen-coverage.mjs   # codegen coverage of every extension over the constructs fixture and examples (--json, --markdown, --base, --root, --badge)
node scripts/ci/codegen-e2e.mjs <django|ash|go|rust>   # generate examples + constructs fixture, build them with the real toolchain
scripts/ci/codegen-e2e-docker.sh <target>             # the same in the target's official docker image (projects in .e2e/)
pnpm sandbox <inspect|openvscode|vscode>                   # a UI sandbox on a copy of examples/ with DevTools on 9222 for the `sandbox` MCP server (ask the user to start it; skill ui-sandbox)
```

CI: `.github/workflows/ci.yml` on every PR and push to `main` runs build, test, `check examples` and the `fmt examples` + `git diff --exit-code` idempotence check, then the codegen coverage report (head and base, one sticky PR comment marked `<!-- appling-codegen-coverage -->`, the badge JSON pushed to the `badges` branch on `main`); see `docs/contributing/development.md`.

`check` and `fmt` run the built CLI (`packages/cli/out/main.js`), so rebuild after any source change. Tests live in `packages/<pkg>/test/`; `packages/lang/test/workspace.ts` builds in memory sources as one workspace. The lang tests import `src/` and only need `langium generate`; every other package's tests import `@appling/*` through the packages' `out/` exports, so rebuild a changed upstream package before testing downstream ones. Every validation rule has a negative fixture in `validation.test.ts`; add one with each new rule. `packages/lang/test/fixtures/constructs/` uses every AST type and keyword of the grammar (`constructs.test.ts` fails otherwise), so extend it with each grammar change; each codegen extension's `coverage.test.ts` plans it and fails when its coverage per node kind (`test/coverage.json`) drops, and `-u` raises the baseline after a gain. Use `pnpm check examples` to verify changes against the sample models; `examples/sales.appling` and `examples/crm.appling` reference each other across modules.

CI: `.github/workflows/codegen-e2e.yml` runs `scripts/ci/codegen-e2e.mjs` once per target (PRs touching codegen, lang, model, cli or examples; nightly; on demand). A generated project that fails to build, warns or fails a test is a generator bug: fix it in the extension with a snapshot or unit test.

## Architecture

- `packages/lang` (`@appling/lang`): the language. `src/appling.langium` is the grammar; `langium generate` writes `src/generated/` (gitignored, never edit). `index.ts` exports the services factory, the printer and the generated AST. `lsp.ts` (subpath export `@appling/lang/lsp`) adds Langium's LSP services with the canonical formatter and a hover; `language-server.ts` is the `appling-language-server` stdio binary.
- `packages/model` (`@appling/model`): the semantic graph. `buildGraph(models, services)` turns resolved models into serializable nodes (qualified name, kind, layer, zoom level, module, props) and edges (`contains`, `uses` for names in expressions, plus one per cross reference, kind = reference property, `decl` becomes `type`); `dependencies(graph)` aggregates module to module edges; `relevance(graph)` (subpath `@appling/model/relevance`, browser safe) scores modules and top level declarations from their dependents and dependencies, mapped into the range of a declared `core`/`supporting`/`peripheral` level (own or inherited from the module, `props.relevance`); `diffGraphs(before, after)` (subpath `@appling/model/diff`, browser safe) lists added, changed (props or edges other than `contains`) and removed elements by qualified name, mapping renames through the migration steps only the graph after has, and `withRemoved` puts removed elements back for a ghosted drawing. Only the kinds in `NAMED` and those with a `keyOf` key become nodes; every other AST node folds into its element's props as canonical text, and its references become edges of that element. A new grammar element kind must be added to one of the two. Declaring lines that are no elements (use case steps and their handlers, `requires`, page components, navigation items, messages) get sub-anchor addresses in `graph.anchors` (`anchors.ts`, subpath `@appling/model/anchors`: `sales.Checkout#step[2]`, `#step[2].on[Declined]`, `#requires[1]`, `#component[1]`, `#item[A/B]`, `#message[key]`), which carry code references and a state (`anchorStates`) without being nodes; a new such line kind goes into `subAnchors`.
- `packages/codegen` (`@appling/codegen`): code generation core. An extension (`CodegenExtension`) maps each graph node to `command`, `template` and `task` steps (`undefined` = unsupported, `[]` = covered by a parent); `plan` orders them by layer and builds one registry entry per node; `runPlan` executes them into the output folder and writes `.appling/tasks.json`. Extensions may add `setup(context)` steps that run once first, and a step `phase` to run after all earlier phases. Extensions read only `GraphNode.data` (structured, references as qualified names, expressions as typed trees), never the Langium AST. Targets come from `appling.config.json` (`generate: [{ extension, out, options }]`). `migrate.ts`: `pendingChanges` turns the model's migration steps (not yet in the project's `.appling/migrations.json`) into changes with the element's qualified name before and now; extensions map each with `migrate(change, context, files)` (each extension's `migrations.ts`); tasks go to the changed element's registry entry. Seed to code (#20): `runPlan(..., written)` collects what each step wrote (`written.ts`: the main run of added lines of a template, the `creates` of a command), `recordWritten` locates it in the final files as code references and records each element's `fingerprint` per target in the workspace's `.appling/generation.json`; `generate.ts` (`generateElements`) generates a selection (outstanding, elements, all) into every target, creating it or merging only the selected elements' files (`mergeGeneration` with a `MergeScope`), and `workspaceImplementation` gives every element its state (`implementationStates` of `@appling/model/implementation`: implemented, partial, unimplemented, shifted, broken).
- `packages/codegen-django` (`@appling/codegen-django`): Django extension. `python.ts` translates expression data to Python (`python`) and to `models.Q` (`q`); `index.ts` dispatches node kinds to `models.ts` (L1), `behavior.ts` (actions, errors, events, machines, jobs), `application.ts` (queries, serializers, externals, use cases) and `api.ts` (REST framework views and routes). `files.ts` merges imports into generated Python files (`pythonFile`); `tests.ts` writes skipped test skeletons whose bodies are registry tasks. Tests apply the template steps in memory; an end to end run needs `uv` and network.
- `packages/codegen-ash` (`@appling/codegen-ash`): Ash extension. `elixir.ts` translates expression data to Ash `expr` bodies and builtin validations; `index.ts` maps nodes to `mix igniter.new` / `ash.gen.*` commands and patches the generated resources (defaults, identities, calculations, validations). Relationships use phase 1 so every resource exists first; every patch of an existing module (`patch()` in `naming.ts`) runs in phase 2, after the last `mix` command, so expressions may follow relationships. `resource.ts` adds lines to (nested) DSL sections and extensions. `behavior.ts` (actions, AshStateMachine, AshOban), `application.ts` (read actions, calculations), `api.ts` (AshJsonApi with a Plug router and Bandit) and `tests.ts` (skipped ExUnit tests).
- `packages/inspect` (`@appling/inspect`, private): the read only inspector, a companion to an AI coding tool (Claude Code, Codex, opencode and the like), run per repo by the VS Code extension and `appling inspect` (published because the CLI depends on it; `appling inspect [folder]` starts it through `startInspectProcess` and opens the client in the browser). It never writes a model file. Subpaths `./process` (`startInspectProcess`), `./panels` and `./host-requests` (`diffMessage`, `openMessage`) serve both apps; in an iframe opened with `?host=frame` the client takes its host hooks over `postMessage` (`src/client/frame-host.ts`, also the host's `theme`: `--appling-*` tokens over its own, `data-theme="light"` for the light palette of `styles.css`), a host with `panels` draws the side panels itself (`src/shared/panels.ts`: the client sends `PanelState` and takes the read only `PanelAction`s `select`, `textDiff` and `review`), the server sends `frame-ancestors` and takes `{ type: 'trust', origin }` over IPC. `src/server` (tsc to `out/`) serves the built client, `/api/snapshot` (files, graph, dependencies, source locations, code references, implementation states, targets, registry tasks), `/api/view` (canvas lens and link entities option in `.appling/view.json`, the only file it writes), `/api/release`, `/api/diff?rev=` (`src/server/git.ts`: the model at a commit through `git ls-tree`/`git show` and the same build, compared with the working tree, plus the changed files from `git diff --name-status` and `git status --porcelain`), `/api/revisions`, `/mcp` (the repo's MCP server per agent session, bearer token; `/api/sessions` opens, renames and ends sessions; `--shared-sessions` takes the store and an `AppHost` from the VS Code extension over IPC) and the websocket `/events` (snapshot pushes on file changes, `live`, `sessions`, `act` and `agent-view` pushes, the client's `context` reports); it binds 127.0.0.1 and checks Host and Origin. `src/client` (React, built by Vite to `dist/client`) is the canvas only: it takes its view logic, tree layout and model canvas from `@appling/viz`, and a selected node opens `Inspector.tsx` floating over the right of the canvas (kind, layer, relations, simulator answers; no editing). `TaskBoard.tsx` lays every registry task (`snapshot.tasks` holds done ones too) over the canvas as in progress, pending and done. `live.ts` (`LiveTracker`) marks every model change against git `HEAD`, or outside git the files on disk at server start, and attributes files written by a session's MCP tool calls; `visuals.ts` (`AgentViews`) is the canvas `VisualHost` of each session's `/mcp`: views and bubbles wait as chips until the user opens them (`AgentView.tsx`). `POST /api/sessions/<id>/ask` delivers a question typed in a session's view to its inbox. `onImplementation` reports implementation marks and code links, which the VS Code extension shows in its editors. Shared types and `buildSnapshot` (the snapshot from file texts) live in `src/shared`. Design tokens follow the landing site. `vite.demo.config.ts` builds the browser only demo into `dist/demo` (base `/inspect/`): it aliases the client's `./api.js` to `src/demo/api.ts`, which keeps `examples/` in memory and answers every server call in the page.
- `packages/viz` (`@appling/viz`): views and canvases. `views.ts` is the pure, tested view logic of the inspector client (`growTree`: the dependency tree of one lens of `LENSES`, domain, behavior, application, interfaces or access, from a seed over modules and the lens's declarations to what uses each unfolded declaration, grouped by kind and ordered by relevance, search, relations by layer with the members they run through, entity actions, action summaries, `trailOf`: the tree that draws only the elements the AI shows one after another, each unfolded in place, the flowcharts `flowView` of a machine or a use case, and the card views `cardView`: one card per action or event); `layout.ts` places the tree growing upwards (rows centered on the most relevant, big folded groups wrapped) and the flowcharts top down (`layoutFlow`, own ranks, no graph library); `canvas/` the read only canvases (`ModelCanvas`, own SVG with pan, zoom and a camera that follows unfolds, circles sized by relevance; `FlowCanvas`; `CardCanvas` as a card grid; `Bubble.tsx` the AI's note and code bubbles; `canvas.css`). `protocol.ts` holds the types of the visual tools (`Show`, `Bubble`, `Review`, `Decision`, `Selection`, `Status`, `nextShow`). The floating Electron window is gone (7C); agent views draw on the inspector's canvas.
- `packages/ai` (`@appling/ai`): `Project` (check, graph, source, edit, registry, tests over a workspace folder), tool definitions with zod schemas in `tools.ts` for the MCP server (`mcp.ts`, bin `appling-mcp`, stdio or `--http`). Tools run against a `ToolContext`: `diskContext` writes files. `createMcpServer` always sends `MCP_INSTRUCTIONS` (`prompts.ts`: the model is the source of truth for business logic). With a `visualizer` (a `VisualHost`; only the inspector server's `AgentViews` for an agent session's `/mcp`) it registers `visualTools` (`visual.ts`: `visualize`, `visual_bubble`, `visual_selection`, `visual_reply`, `visual_status`); the stdio and `--http` servers have no visual tools. With a `session` (`{ id, store, host }`) it adds the session tools (`session-tools.ts`: label, status, claims, list, messages, `ide_context`, `ide_act`), attributes every call to the session and adds `conflicts` and a `warning` to edits that touch another session's claims. `sessions.ts` holds `SessionStore` (`MemorySessionStore`; `serveSessionStore`/`RemoteSessionStore` share one over an IPC `Channel`). The registry skill text lives once in `skills/appling-registry/SKILL.md` and doubles as the MCP prompt. `agents/` (subpath `@appling/ai/agents`, used by the VS Code extension): `presets.ts` with Claude Code, Codex, Gemini CLI, opencode and `agents.presets`, `launch` building command, args, env and config files that wire the MCP server without touching user config; `status.ts`, the status state machine from hooks, OSC 9/777 and the exit; `gateway.ts`, one local endpoint: `/mcp` forwards to the session's repo server, `/hooks/<event>`; `hook.cts`, the command hook client the build copies to `out/agents/hook.cjs`. There is no built in chat and no AI SDK dependency: AI runs through agents in terminals (agent sessions).
- `packages/pty-host` (`@appling/pty-host`, private, issues #9 and #18): the per user daemon that owns an app's terminals so they outlive the app, the way VS Code's ptyHost works. `host.ts` (`PtyHost`) spawns shells (with `attach` the spawning client gets the output from the first byte, `spawnAttached`) with `node-pty`, mirrors each into an `@xterm/headless` terminal and on `attach` replays it with `@xterm/addon-serialize` (the snapshot is taken in a `write('')` callback; output arriving meanwhile is queued for that client, so nothing is lost or doubled); ended terminals keep their scrollback until killed. `protocol.ts` is newline delimited JSON over a Unix socket (Windows: a named pipe) in a 0700 folder (`paths.ts`: `APPLING_PTY_HOST_DIR`, else `$XDG_RUNTIME_DIR` or the temp folder); a client must first send a `hello` with the token the host writes to that folder on every start. `client.ts`: `connectPtyHost` connects or starts the host detached (`main.js serve`, its own session, output to `pty-host.log`), `PtyHostClient`, `AttachedTerminal` (buffers output until the first `onData`). A lock folder lets only one of two hosts started at once listen; the host exits after `--idle-timeout` without authenticated clients and running terminals. `status.ts` keeps each terminal's status from its output (running, `needsInput` after OSC 9/777 until the next input, exited) and `meta` is free spawn metadata; subscribed clients get `terminal`, `status` and `removed` events. With nobody attached to a terminal that needs input the host calls its injected `Notifier` (`notifier.ts`: `systemNotifier`, gdbus or notify-send, osascript, a PowerShell toast); a click runs the `open` command, a reply goes to the pty. Status and notifier are transport independent: a remote host runs with `notify: false`. `appling-pty-host list|kill|stop` work without the app. The VS Code extension uses only `@appling/pty-host/status`. node-pty is N-API, so the same build loads under Electron with `ELECTRON_RUN_AS_NODE`. Tests start real hosts in temp folders and run against the built `out/main.js`.
- `packages/vscode` (`appling-vscode`, private): the VS Code extension. `scripts/bundle.mjs` bundles `src/extension.ts` (a `vscode-languageclient`) and the language server from `@appling/lang` (CommonJS), the inspector server with its client and the AI skills (`out/inspect/`, ESM), the CLI (`out/cli/`) and the agents' hook into `out/`, then `vsce` writes `out/appling.vsix`; the TextMate grammar comes from Langium (`packages/lang/src/syntaxes/`, generated next to the Monarch grammar). `workbench.ts`: the projects (`projects.ts`: folders with `appling.config.json`, workspace folders with loose models), one inspector server per project (`startInspectProcess`, on VS Code's Node, sharing one session store), the Projects view with modules, the inspector tab per project (a webview iframe of the client with `?host=frame`, `frame.ts`: the page, the relay with VS Code's theme for the inspector's tokens (`THEME_TOKENS`) and `panelAction`, which checks the client's requests), the inspector's side panels as read only native trees in the Appling sidebar (`panel-trees.ts`, VS Code free, builds them from the client's `PanelState`: Inspector, Changes, Review, Code and Tasks, search being the language server's workspace symbols; `panels.ts` the views and their commands), **Appling: Show in the inspector** in a `.appling` editor's title, the implementation marks of every project, and **Initialize Appling** (the bundled `appling init` in a terminal). `agents.ts` (VS Code free, injected terminals), `agent-terminals.ts` (shell integration `executeCommand`, OSC notifications through `@appling/pty-host/status`) and `agents-view.ts` (the Agent Sessions view, answers, notifications, `appling.agents.presets`) run agent sessions in VS Code terminals on `@appling/ai/agents`.
- `packages/landing` (`@appling/landing`, private): the Astro 7 + Tailwind 4 landing site. Pages live in `src/pages/`, share `src/layouts/Layout.astro` (header, footer) and the design tokens in `src/styles/global.css`. The design source for every page is the Design canvas https://claude.ai/artifact/KLixzPpo9HLrXJG21jWkVC (one artboard per page, built on the Appling design system); implement new pages from their artboard there. It also renders the user documentation from the repo's `docs/` folder at `/docs` (`src/content.config.ts`, sidebar in `src/docs.ts`, `src/markdown.ts` validates `appling check`/`appling graph` examples against `@appling/lang` and draws their graph with Mermaid), so it builds after `lang` and `model`. `Showcase.astro` embeds the inspector demo, loaded in an iframe on click: the `inspect-demo` integration in `astro.config.mjs` serves `packages/inspect/dist/demo` at `/inspect/` in `astro dev` and copies it into the build, so build `@appling/inspect` first. Every push to `main` builds and deploys it to Bunny (`.github/workflows/deploy.yml`); checks run in `ci.yml`.
- `packages/cli` (`@appling/cli`): the `appling` binary, among its commands `inspect [folder]` (`inspect.ts`: the inspector server of `@appling/inspect/process` on a free port, opened in the browser with `open`, until Ctrl+C) and `check` (build with validation, print diagnostics), `fmt` (requires a syntax error free parse, then prints canonically and writes back) `graph` (validated build, then the semantic graph as JSON on stdout; diagnostics go to stderr) `release <version>` (validated build, then a graph snapshot in `.appling/releases/`) and `generate [--plan]` (code generation per configured target). All given files load as one workspace so cross file module references resolve. Exit codes: 0 no errors, 1 `check`/`graph`/`release` errors (or an invalid or existing release version) or `fmt` skipped a file, 2 unknown command or missing version. `fmt` must be idempotent: a second run changes nothing.

Each package has a user facing `README.md` (published to npm) documenting the CLI usage and exit codes, the language overview, its rules and the public API. Keep them in sync when changing CLI behavior, grammar keywords, validation rules or exports from `index.ts`. The full user documentation lives in `docs/` (everything except `concept.md` and `ROADMAP.md` is user facing); `pnpm --filter @appling/landing... build` validates its examples.

Key mechanics that span several files:

- **Identity and migrations.** Elements are identified by their qualified name; there are no separate ids. Migration steps (`rename`/`retype`/`remove`) target a path inside their module as it was before the step. `checkMigration` replays the later steps of the same module (in declaration order) to find where that path lives now, then requires it to exist (rename, retype) or not exist (remove).
- **Scoping** (`appling-scope.ts`). Inside a module, nested elements are visible by dotted path (`Order.status`). Across modules (and files) only members listed in `export` are visible, by module path (`sales.Order`, nested modules `a.b.X`). The scope provider special cases `picks` (fields of the referenced projection), `sort` (fields of the query entity), `set` (fields of the action's entity or the machine's entity) and error handlers (errors of the called action or external op).
- **Layer rules** (`appling-validator.ts`). `LAYER_OF` maps every top level member type to a layer; `checkLayerReferences` walks every cross reference and applies `isAllowed`, which encodes the reference DAG from `docs/concept.md` section 2.3. A new member type must be added to `LAYER_OF`.
- **Expressions** (`appling-types.ts`) are a CEL subset parsed into plain AST nodes. Names inside expressions are strings, not cross references; `ExpressionTyper` resolves them per position (`contextOf`), types every root expression and call, and records `targets` (the element each name stands for). The validator reports its problems; the graph turns targets into `uses` edges; renames must follow them. `actor.is(x)` resolves through `ApplingScopeProvider.lookup`. A new construct that holds an expression needs a branch in `contextOf`, or its expressions are not typed.
- **Edit operations** (`packages/model/src/edit.ts`). `applyEdit(sources, op)` finds the target by qualified name, splices text (rename and retype touch only tokens; add, remove and set reprint the touched element with `printRange`), rebuilds and rejects the edit when it adds an error. Rename has to find every place that names an element; a new way of naming elements (a new reference kind is automatic, but string names like `export` lists, message keys or transition states are not) must be added to `renameSplices`.
- **Releases** (`packages/model/src/release.ts`). `appling release <version>` writes the graph to `.appling/releases/<version>.json`. `applyEdit(..., { release })` appends `rename`/`retype`/`remove` steps for released L1 elements to the module's `since_v<version>` block (`migrationStep`, `appendStep`), mapping current paths back to released ones through that block's renames.
- **Canonical printer** (`appling-printer.ts`). Walks the CST leaves and decides every gap between tokens, keeping comments. `printRange(node)` renders the whole document and returns just one node's canonical text with its surrounding gaps. Layout is driven by the `BLOCKS` (node types whose `{` opens an indented block) and `CLAUSES` (keywords that start their own line inside a block) sets; new block or clause constructs in the grammar must be registered there or they print inline.
- **Scenarios** (`scenario`, outside the layers: `LAYER_OF` gives `cross`, `isAllowed` lets it reference anything). Helpers in `appling-scenario.ts`; the typer types given rows, actor fields, call arguments and checks (`scenarioEnv`). `Simulator.scenario(qn)` runs one; `checkScenarios` in `packages/model/src/scenarios.ts` turns failures into errors, which the CLI's `check` and the MCP `check` tool report once nothing else fails (the validator cannot, `lang` does not depend on `model`). Generators write one test per scenario and skip their guessed tests for `coveredByScenarios(graph)`; `plan` orders scenarios last.

Grammar conventions: keywords that should remain valid as names (fields like `state`, `order`) must also be listed in the `Ident` rule. References use `[Type:QualifiedName]` except for local lookups (`[Field:Ident]`, `[ErrorDecl:Ident]`) that the scope provider resolves.
