# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Appling: a declarative DSL (`.appling` files) that models a business application across five layers (Domain, Behavior, Application, Interfaces, Experience) plus cross cutting concepts (modules, roles, actors, tenants, migrations). The text is the canonical source of truth; the end goal is a validated semantic graph for visualization, simulation and AI editing; code generation produces a draft project for a target framework through installable extensions (Django and Ash first). `docs/concept.md` is the design spec (layer ownership, reference rules, narrowing, identity by qualified name) and is the authority when grammar or validation decisions are unclear. `docs/ROADMAP.md` lists the planned packages, phases and decisions.

## Commands

pnpm workspace (`packages/*`), Node 24 (`.nvmrc`), TypeScript 7, Langium 4.4, vitest 5. There is no linter. Use the pinned pnpm (`corepack pnpm`); a global pnpm 8 cannot install into this workspace. `pnpm-workspace.yaml` lists packages exempt from the minimum release age; a newly published dependency needs an entry there.

```sh
pnpm install
pnpm build                  # every package in dependency order (langium generate + tsc in lang, vite for the IDE client, astro for landing)
pnpm check [paths...]       # validate .appling files (default: current dir, recursive)
pnpm fmt [paths...]         # rewrite files into canonical form
node packages/cli/out/main.js graph [paths...]   # semantic graph as JSON
pnpm test                   # vitest over packages/*/test
pnpm vitest run packages/lang/test/validation.test.ts -t "name"   # one file, one test
pnpm vitest run -u          # update snapshots (model, codegen-django, codegen-ash)
node packages/ide/out/server/main.js examples   # the IDE on http://127.0.0.1:4410 (ask the user to start it)
pnpm --filter @appling/lang build   # rebuild only the language after grammar changes
```

`check` and `fmt` run the built CLI (`packages/cli/out/main.js`), so rebuild after any source change. Tests live in `packages/<pkg>/test/`; `packages/lang/test/workspace.ts` builds in memory sources as one workspace. The lang tests import `src/` and only need `langium generate`; every other package's tests import `@appling/*` through the packages' `out/` exports, so rebuild a changed upstream package before testing downstream ones. Every validation rule has a negative fixture in `validation.test.ts`; add one with each new rule. Use `pnpm check examples` to verify changes against the sample models; `examples/sales.appling` and `examples/crm.appling` reference each other across modules.

## Architecture

- `packages/lang` (`@appling/lang`): the language. `src/appling.langium` is the grammar; `langium generate` writes `src/generated/` (gitignored, never edit). `index.ts` exports the services factory, the printer and the generated AST. `lsp.ts` (subpath export `@appling/lang/lsp`) adds Langium's LSP services with the canonical formatter and a hover; `language-server.ts` is the `appling-language-server` stdio binary.
- `packages/model` (`@appling/model`): the semantic graph. `buildGraph(models, services)` turns resolved models into serializable nodes (qualified name, kind, layer, zoom level, module, props) and edges (`contains`, `uses` for names in expressions, plus one per cross reference, kind = reference property, `decl` becomes `type`); `dependencies(graph)` aggregates module to module edges; `relevance(graph)` (subpath `@appling/model/relevance`, browser safe) scores modules and top level declarations from their dependents and dependencies, mapped into the range of a declared `core`/`supporting`/`peripheral` level (own or inherited from the module, `props.relevance`). Only the kinds in `NAMED` and those with a `keyOf` key become nodes; every other AST node folds into its element's props as canonical text, and its references become edges of that element. A new grammar element kind must be added to one of the two.
- `packages/codegen` (`@appling/codegen`): code generation core. An extension (`CodegenExtension`) maps each graph node to `command`, `template` and `task` steps (`undefined` = unsupported, `[]` = covered by a parent); `plan` orders them by layer and builds one registry entry per node; `runPlan` executes them into the output folder and writes `.appling/tasks.json`. Extensions may add `setup(context)` steps that run once first, and a step `phase` to run after all earlier phases. Extensions read only `GraphNode.data` (structured, references as qualified names, expressions as typed trees), never the Langium AST. Targets come from `appling.config.json` (`generate: [{ extension, out, options }]`). `migrate.ts`: `pendingChanges` turns the model's migration steps (not yet in the project's `.appling/migrations.json`) into changes with the element's qualified name before and now; extensions map each with `migrate(change, context, files)` (each extension's `migrations.ts`); tasks go to the changed element's registry entry.
- `packages/codegen-django` (`@appling/codegen-django`): Django extension. `python.ts` translates expression data to Python (`python`) and to `models.Q` (`q`); `index.ts` dispatches node kinds to `models.ts` (L1), `behavior.ts` (actions, errors, events, machines, jobs), `application.ts` (queries, serializers, externals, use cases) and `api.ts` (REST framework views and routes). `files.ts` merges imports into generated Python files (`pythonFile`); `tests.ts` writes skipped test skeletons whose bodies are registry tasks. Tests apply the template steps in memory; an end to end run needs `uv` and network.
- `packages/codegen-ash` (`@appling/codegen-ash`): Ash extension. `elixir.ts` translates expression data to Ash `expr` bodies and builtin validations; `index.ts` maps nodes to `mix igniter.new` / `ash.gen.*` commands and patches the generated resources (defaults, identities, calculations, validations). Relationships use phase 1 so every resource exists first; every patch of an existing module (`patch()` in `naming.ts`) runs in phase 2, after the last `mix` command, so expressions may follow relationships. `resource.ts` adds lines to (nested) DSL sections and extensions. `behavior.ts` (actions, AshStateMachine, AshOban), `application.ts` (read actions, calculations), `api.ts` (AshJsonApi with a Plug router and Bandit) and `tests.ts` (skipped ExUnit tests).
- `packages/ide` (`@appling/ide`): local web IDE. `src/server` (tsc to `out/`) serves the built client, `/api/snapshot` (files, graph, dependencies, source locations), `/api/file`, `/api/view` (canvas lens and link entities option in `.appling/view.json`), `/api/edit` (runs `applyEdit` on the texts the client sends, with the latest release; writes nothing), `/api/release`, `/api/chat` (NDJSON stream of `@appling/ai` chat events), and websockets `/events` (snapshot pushes on file changes) and `/lsp` (one Langium language server per connection); it binds 127.0.0.1 and checks Host and Origin. `src/client` (React, Monaco with its bundled LSP client, built by Vite to `dist/client`) takes its view logic, tree layout and model canvas from `@appling/viz`; the canvas is read only, `Search.tsx` and `Inspector.tsx` in the side panel open every other element. Edits from the inspector go to `/api/edit`; the returned text edits are applied to the Monaco models as undoable steps (`applyTextEdits`) and saved. A model is dirty while its text differs from the last disk text. Shared types and `buildSnapshot` (the snapshot from file texts) live in `src/shared`. Design tokens follow the landing site. `vite.demo.config.ts` builds the browser only demo into `dist/demo` (base `/ide/`): it aliases the client's `./api.js` to `src/demo/api.ts`, which keeps `examples/` in memory, answers every server call in the page (edits through `@appling/model/edit`, no chat) and runs the language server in a worker (`src/demo/language-server.ts`).
- `packages/viz` (`@appling/viz`): views and windows. `views.ts` is the pure, tested view logic shared with the IDE (`growTree`: the dependency tree of one lens of `LENSES`, domain, behavior, application, interfaces or access, from a seed over modules and the lens's declarations to what uses each unfolded declaration, grouped by kind and ordered by relevance, search, relations by layer with the members they run through, entity actions, action summaries, and the card views `cardView`: per state of a machine what can be done there, and one card per action, use case or event); `layout.ts` places the tree growing upwards (rows centered on the most relevant, big folded groups wrapped); `canvas/` the read only canvases (`ModelCanvas`, own SVG with pan, zoom and a camera that follows unfolds, circles sized by relevance; `CardCanvas` as a card grid; `canvas.css`). `host.ts` (`Visualizer`) serves the floating window (`src/window`, built by Vite to `dist/window`) on 127.0.0.1 with a token, starts Electron (`main/electron.ts`: frameless, always on top, top right, `--ozone-platform=x11` on Wayland) and talks to it over one websocket (`protocol.ts`); tests inject `launch`. Electron downloads its binary on first use and prints to stdout, so `host.ts` triggers that in a child whose stdout goes to stderr.
- `packages/ai` (`@appling/ai`): `Project` (check, graph, source, edit, registry, tests over a workspace folder), tool definitions with zod schemas in `tools.ts` shared by the MCP server (`mcp.ts`, bin `appling-mcp`, stdio or `--http`) and the AI SDK chat (`chat.ts`). Tools run against a `ToolContext`: `diskContext` writes files, `ProposalContext` collects edits on a working copy for review. `createMcpServer` always sends `MCP_INSTRUCTIONS` (`prompts.ts`: the model is the source of truth for business logic). Over stdio `main.ts` passes a `Visualizer` to `createMcpServer`, which then registers `visualTools` (`visual.ts`: `visualize`, `visual_selection`, `visual_reply`, `propose_edits`, which waits for the decision in the window) and declares the `claude/channel` capability; questions typed into the window become `notifications/claude/channel`. The registry skill text lives once in `skills/appling-registry/SKILL.md` and doubles as the MCP prompt. Default model `claude-opus-5-5` through `@ai-sdk/anthropic`; the `ai` section of `appling.config.json` can switch provider (`anthropic` or `openai`) and model, keys come from the environment; tests use `MockLanguageModelV4`, never a real API.
- `packages/vscode` (`appling-vscode`, private): the VS Code extension. esbuild bundles `src/extension.ts` (a `vscode-languageclient`) and the language server from `@appling/lang` into `out/`; the TextMate grammar comes from Langium (`packages/lang/src/syntaxes/`, generated next to the Monarch grammar). `pnpm --filter appling-vscode package` writes `out/appling.vsix`.
- `packages/landing` (`@appling/landing`, private): the Astro 7 + Tailwind 4 landing site. Pages live in `src/pages/`, share `src/layouts/Layout.astro` (header, footer) and the design tokens in `src/styles/global.css`. The design source for every page is the Design canvas https://claude.ai/artifact/KLixzPpo9HLrXJG21jWkVC (one artboard per page, built on the Appling design system); implement new pages from their artboard there. It also renders the user documentation from the repo's `docs/` folder at `/docs` (`src/content.config.ts`, sidebar in `src/docs.ts`, `src/markdown.ts` validates `appling check`/`appling graph` examples against `@appling/lang` and draws their graph with Mermaid), so it builds after `lang` and `model`. `Showcase.astro` embeds the IDE demo, loaded in an iframe on click: the `ide-demo` integration in `astro.config.mjs` serves `packages/ide/dist/demo` at `/ide/` in `astro dev` and copies it into the build, so build `@appling/ide` first. Every push to `main` builds and deploys it to Bunny (`.github/workflows`); it is the only CI job.
- `packages/cli` (`@appling/cli`): the `appling` binary with five commands, `check` (build with validation, print diagnostics), `fmt` (requires a syntax error free parse, then prints canonically and writes back) `graph` (validated build, then the semantic graph as JSON on stdout; diagnostics go to stderr) `release <version>` (validated build, then a graph snapshot in `.appling/releases/`) and `generate [--plan]` (code generation per configured target). All given files load as one workspace so cross file module references resolve. Exit codes: 0 no errors, 1 `check`/`graph`/`release` errors (or an invalid or existing release version) or `fmt` skipped a file, 2 unknown command or missing version. `fmt` must be idempotent: a second run changes nothing.

Each package has a user facing `README.md` (published to npm) documenting the CLI usage and exit codes, the language overview, its rules and the public API. Keep them in sync when changing CLI behavior, grammar keywords, validation rules or exports from `index.ts`. The full user documentation lives in `docs/` (everything except `concept.md` and `ROADMAP.md` is user facing); `pnpm --filter @appling/landing... build` validates its examples.

Key mechanics that span several files:

- **Identity and migrations.** Elements are identified by their qualified name; there are no separate ids. Migration steps (`rename`/`retype`/`remove`) target a path inside their module as it was before the step. `checkMigration` replays the later steps of the same module (in declaration order) to find where that path lives now, then requires it to exist (rename, retype) or not exist (remove).
- **Scoping** (`appling-scope.ts`). Inside a module, nested elements are visible by dotted path (`Order.status`). Across modules (and files) only members listed in `export` are visible, by module path (`sales.Order`, nested modules `a.b.X`). The scope provider special cases `picks` (fields of the referenced projection), `sort` (fields of the query entity), `set` (fields of the action's entity or the machine's entity) and error handlers (errors of the called action or external op).
- **Layer rules** (`appling-validator.ts`). `LAYER_OF` maps every top level member type to a layer; `checkLayerReferences` walks every cross reference and applies `isAllowed`, which encodes the reference DAG from `docs/concept.md` section 2.3. A new member type must be added to `LAYER_OF`.
- **Expressions** (`appling-types.ts`) are a CEL subset parsed into plain AST nodes. Names inside expressions are strings, not cross references; `ExpressionTyper` resolves them per position (`contextOf`), types every root expression and call, and records `targets` (the element each name stands for). The validator reports its problems; the graph turns targets into `uses` edges; renames must follow them. `actor.is(x)` resolves through `ApplingScopeProvider.lookup`. A new construct that holds an expression needs a branch in `contextOf`, or its expressions are not typed.
- **Edit operations** (`packages/model/src/edit.ts`). `applyEdit(sources, op)` finds the target by qualified name, splices text (rename and retype touch only tokens; add, remove and set reprint the touched element with `printRange`), rebuilds and rejects the edit when it adds an error. Rename has to find every place that names an element; a new way of naming elements (a new reference kind is automatic, but string names like `export` lists, message keys or transition states are not) must be added to `renameSplices`.
- **Releases** (`packages/model/src/release.ts`). `appling release <version>` writes the graph to `.appling/releases/<version>.json`. `applyEdit(..., { release })` appends `rename`/`retype`/`remove` steps for released L1 elements to the module's `since_v<version>` block (`migrationStep`, `appendStep`), mapping current paths back to released ones through that block's renames.
- **Canonical printer** (`appling-printer.ts`). Walks the CST leaves and decides every gap between tokens, keeping comments. `printRange(node)` renders the whole document and returns just one node's canonical text with its surrounding gaps. Layout is driven by the `BLOCKS` (node types whose `{` opens an indented block) and `CLAUSES` (keywords that start their own line inside a block) sets; new block or clause constructs in the grammar must be registered there or they print inline.

Grammar conventions: keywords that should remain valid as names (fields like `state`, `order`) must also be listed in the `Ident` rule. References use `[Type:QualifiedName]` except for local lookups (`[Field:Ident]`, `[ErrorDecl:Ident]`) that the scope provider resolves.
